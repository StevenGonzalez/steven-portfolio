Before the saws, I worked on a SaaS platform that gyms, studios and multi-location operators run their businesses on: scheduling, billing, leads, member features and reporting. The same code serves a single studio and a national franchise, and each of them runs differently.

What I learned there is that most of the work in a feature is everything else it touches.

## "Let a member book a class"

It sounds like one button. Then the questions start.

Is the membership active? Does it include this class? Is the class full, and is there a waitlist? Can staff override that? What if the last payment failed? What if the member belongs to another location? What if the class moved, got cancelled or changed instructors after they booked? And reporting will later want to tell a no-show from a late cancel.

That one button reaches into scheduling, billing, membership rules, permissions and reporting. The UI is small and the behavior isn't. So before changing anything, I learned to map what it touches.

## Every setting multiplies the cases

Configuration is how one product fits many different businesses. It's also how a change that works for one customer breaks for another, because of a membership rule, a tax setting, a staff permission or a location policy nobody thought to test.

The default setup almost never looks like a real customer's. I treat settings as part of what needs testing: which ones interact, which combinations are common, and which are risky. Sometimes the better fix is changing the model so a bad combination can't exist, instead of adding one more if-statement.

## Whose data is it?

In a multi-tenant system, every query carries a second question: is this the right customer's data? Tenant IDs, location scoping, role checks and report filters look like plumbing. They are what lets many businesses share one system safely.

They also shape how features get built. A query that's fast on a dev database can be slow on production data. A report that's right for one location can be wrong across several. A background job that touches shared tables needs the same filtering as a request, and logs that show it did.

A correct number belongs to the right customer, follows that customer's rules, and means what they think it means.

## Reports find the vague parts

Day to day, staff can work around a fuzzy state because they know the context. Reports can't. They add things up, and owners make decisions from them: revenue, attendance, payroll, retention.

So reporting is where an unclear workflow shows itself. What counts as a completed booking? When does revenue count? How does a refund show up? Is a staff override recorded as one? Each of those is a product decision. If the data model doesn't record the answer clearly, every report answers it a little differently.

## Somebody's normal day

Bugs here land on real people. A billing mistake can reach someone's payroll. A scheduling bug can leave a member at the front desk for a class that isn't there. A permissions mistake can show data to the wrong person.

Keeping that in mind changed how I build: more validation, clearer error states, careful migrations, and asking who relies on a behavior and how they'd notice if it broke.
