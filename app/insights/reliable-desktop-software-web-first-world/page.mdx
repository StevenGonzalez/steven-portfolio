_Update, Oct 2026: after a year and a half, the company cancelled the rewrite to put its people on other work._

At work I led a rewrite of the software that runs industrial saws. The operator interface was Angular, the back end was a C# API, and Electron.NET packaged both into one desktop app. RabbitMQ carried messages between the saw software and other programs, and a PLC integration talked to the machine itself.

Most of that stack is ordinary web tech. But it ran a machine with someone standing next to it, and that changed how I built it.

## Releases

A website updates when you deploy it, and everyone gets the new version on their next page load. A desktop release is a build that gets installed on a machine and stays there.

So every release shipped as one build with the UI, the API and the runtime together, and there was never a question of which front end was talking to which back end. For any release, I wanted to be able to say:

- what version of each piece is inside it
- how the app finds its local services
- where it writes its logs
- what the operator sees if startup fails

## What the screen shows

In a web app, a button stuck waiting on a slow API is annoying. When the button controls a saw, the operator needs to know whether the command actually happened.

Every command goes from the UI to the API, from the API to the message bus, and then to the machine, and any of those steps can be slow, down or only partly done. So the UI shows only what the system knows: connected or not, busy, waiting, done, failed. I avoided optimistic updates here, because operators stop believing a screen that shows states the machine hasn't confirmed.

## Layers

The machine has its own timing and its own ways of failing, and none of that belonged in the Angular components. We kept the UI, the API and messaging as separate layers that could change independently, with fixed paths for talking to the machine.

The UI shows the workflow and stays quick because it runs locally. The API checks a command before it goes anywhere. Messaging moves it between programs. The PLC layer handles the protocol. Anything that touches the machine goes through explicit services and message contracts that we can watch, so a change to the UI can't quietly change how the machine behaves.

## Small changes

Most changes had to line up across the UI, the API, the message contracts and the machine. I preferred small changes, done in order and tested one at a time, over one bigger change across all four layers at once, so that when something went wrong there were fewer places to look.
