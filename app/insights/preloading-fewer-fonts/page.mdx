This site's CI loads its pages in Lighthouse as a phone would and fails the build if first contentful paint goes over 1 s or largest contentful paint goes over 3.5 s. Project pages were at 3.24 s for largest paint, so I tried to buy some room. The change made first paint worse by 0.76 s, I reverted it, and then I went to find out why.

## The change

The site preloads five font files, 152 KB in all. Lighthouse named the header wordmark as the home page's largest paint, and the wordmark uses one of those fonts. The italic and the two mono weights only set small labels and captions, so I stopped preloading those three, which left 83 KB.

CI's first contentful paint on the home page went from 0.91 s to 1.67 s, over the limit. Largest paint stayed at 2.87 s.

## How Lighthouse got 1.67 s

By default Lighthouse does not slow the browser down. It loads the page at full speed, records every request, and then estimates what the load would have taken on a slow phone. The estimator is called Lantern, and it has to decide which requests the first paint waited for. It decides mostly by the priority Chrome gave each request:

```js
hasRenderBlockingPriority() {
  const priority = this._request.priority;
  const isScript = this._request.resourceType === 'Script';
  const isDocument = this._request.resourceType === 'Document';
  const isBlockingScript = priority === 'High' && isScript;
  const isBlockingHtmlImport = priority === 'High' && isDocument;
  return priority === 'VeryHigh' || isBlockingScript || isBlockingHtmlImport;
}
```

A font at `High` does not count. A font at `VeryHigh` does. Chrome gives a preloaded font `High`, and a font it finds through the stylesheet `VeryHigh`. I confirmed that with a small proxy in front of the production build that removed the three preload tags from the HTML and changed nothing else:

```
                                 preloaded    found through CSS
cormorant_garamond               High         High (still preloaded)
schibsted_grotesk                High         High (still preloaded)
cormorant_garamond_italic        High         VeryHigh
ibm_plex_mono_400                High         VeryHigh
ibm_plex_mono_500                High         VeryHigh
```

So the three fonts I had stopped preloading became requests the first paint was assumed to wait for. These fonts use `font-display: swap`, so the browser paints text in a fallback font without waiting for them. The estimate had no way of knowing that.

## Slowing the browser for real

Lighthouse has a second mode, `throttlingMethod: "devtools"`, which slows the network and the CPU during the load. I ran both modes against the same build, with and without the three preloads. First contentful paint, in milliseconds:

```
                              simulated          really slowed
page                          5 fonts  2 fonts   5 fonts  2 fonts
/                             907      1658      1951     1766
/projects/sky-islands         907      1509      1804     1687
/projects/virtual-trainer     906      1508      1817     1771
```

Lantern's numbers reproduce what CI saw. With the browser really slowed, the page painted 46 to 185 ms sooner with fewer preloads. That was one run per cell on a machine doing other work, so I would not lean on the size of the difference. The direction is the opposite of the estimate.

Largest paint has a related quirk. Lantern's graph for it includes every request that started before the largest paint was observed, apart from low-priority images, so scripts loading in the background count. On `/projects/sky-islands` it estimated between 2.6 and 3.2 s, depending on the run. Really slowed, the largest paint was the same frame as the first paint, at about 1.75 s. The number I had been trying to lower mostly follows how much JavaScript and font data a page starts loading early.

## The subtitle

The really slowed runs also showed a problem that the estimate had hidden. On the home page, first paint was at about 1.9 s and largest paint at about 3.8 s, later than the simulated 2.9 s. Lighthouse named the element, and it was not the wordmark. It was the subtitle under my name.

The hero text had an entrance animation that started each line at `opacity: 0`, and the subtitle's began after a 0.7 s delay and ran for 1 s. Those two numbers are almost exactly the gap between first paint and largest paint. On a slow phone, the line that says what I do was invisible for nearly two seconds after the page had painted.

The name and the subtitle now only move, without fading, so they are readable in the first frame:

```css
.copy > :nth-child(2),
.copy > :nth-child(3) {
  animation-name: settle;
}
@keyframes settle {
  from {
    transform: translateY(16px);
  }
}
```

Three runs before the change put the home page's largest paint at 3,729, 3,965 and 3,695 ms. Three runs after it put it at 1,848, 1,871 and 1,876 ms, in the same frame as first paint, and the element is now the name. Lantern's estimate for the page did not move, at about 2.9 s both times.

## What I kept

All five fonts are still preloaded, because the possible gain from dropping three was small and uncertain and CI would have failed. The limits in CI are unchanged. It still catches a page that starts shipping much more JavaScript.
